# 로봇 Wi-Fi 지연 진단 · 2026-10-05

데스크톱에서 젯슨(`192.168.50.124`)으로 보내는 핑이 느리고 들쭉날쭉했다. 원인은 두 가지였고 둘 다 고쳤다.

## 결과

데스크톱 → 젯슨, ICMP 0.2초 간격.

| | 중앙값 | p90 | p99 | 최대 | 50 ms 넘은 핑 |
|---|---|---|---|---|---|
| 고치기 전 (150회) | 52.1 ms | 105.0 ms | 292.0 ms | 302.0 ms | 76회 (51 %) |
| 젯슨 절전만 끈 뒤 (150회) | 6.3 ms | 51.5 ms | 122.0 ms | 127.0 ms | 15회 |
| **모두 고친 뒤 (300회)** | **4.8 ms** | **8.3 ms** | **16.8 ms** | **34.8 ms** | **0회** |

손실은 모든 측정에서 0이었다. 고친 뒤 60초 동안 젯슨·데스크톱 모두 Wi-Fi 스캔 0회.

## 네트워크 구성

| 장비 | 주소 | 연결 |
|---|---|---|
| **TP-Link EAP225** (실제 무선 AP) | 192.168.50.2 | SSID `ROBOT`(2.4 GHz, 11채널) / `ROBOT5G`(5 GHz, 44채널) |
| 라즈베리파이 (`suhopi`) | 192.168.50.1 | 유선(eth0)으로 EAP225 에 연결. DHCP 서버·게이트웨이 역할만 (무선 꺼짐, 인터넷 경로 없음) |
| 젯슨 (`parksudo`) | 192.168.50.124 | `ROBOT5G`, 신호 -33 dBm, 866 Mbps (Intel AX210, iwlwifi) |
| 데스크톱 USB 동글 | 192.168.50.189 | `ROBOT`, 신호 -36 dBm, 144 Mbps (RTL8192EU) |

신호와 속도는 양쪽 모두 아주 좋다. 링크 품질 문제가 아니었다.

## 어디서 느렸나

데스크톱 → 라즈베리파이(192.168.50.1)와 데스크톱 → 젯슨을 **동시에** 쟀다. 라즈베리파이까지 가는 길은
데스크톱 → EAP225(무선) → 라즈베리파이(유선)라서, 이 값이 정상이면 데스크톱 쪽 무선 구간은 정상이다.

- 데스크톱 → 라즈베리파이: 중앙 3.6 ms, 최대 26 ms (정상)
- 데스크톱 → 젯슨: 중앙 52.1 ms, 최대 302 ms

→ **AP에서 젯슨으로 가는 구간**이 문제였다. 젯슨 → AP 방향 핑은 평균 5.5 ms로 빨랐다.
젯슨이 보낼 때는 스스로 깨어 있고, **밖에서 젯슨으로 들어오는 쪽만** 느렸다는 뜻이다.

젯슨 지연은 53 → 58 → 67 → 81 → 95 → 105 ms처럼 **계단식으로 오르다 떨어지는 톱니 모양**이었다.
Wi-Fi 절전 단말이 비콘 주기(약 100 ms)마다만 깨어나서 AP가 그동안 패킷을 붙잡고 있을 때 나오는 전형적인 모양이다.

## 원인 1 — 젯슨 Wi-Fi 절전이 켜져 있었다

`iw dev wlP1p1s0 get power_save` → **on**

9월 26일에 절전을 끄는 설정 파일(`99-gen2-wifi-powersave-off.conf`)을 넣었는데 **한 번도 적용된 적이 없었다.**

NetworkManager는 `/etc/NetworkManager/conf.d/`의 파일을 **이름순으로 읽고, 나중에 읽은 파일이 이긴다.**

```
99-gen2-wifi-powersave-off.conf    ← 끄기 (2)
default-wifi-powersave-on.conf     ← 켜기 (3, Ubuntu 패키지 파일)  ← 마지막에 읽혀서 이김
```

숫자 `9`가 글자 `d`보다 앞이라 패키지 기본값이 마지막에 읽혔다. 실제 적용값을 찍어 보면:

```
$ NetworkManager --print-config | grep powersave
wifi.powersave=3        ← 켜짐
```

9월 26일에 좋아진 건 런타임 명령(`iw ... set power_save off`) 덕분이었고, 오늘 재부팅하면서 다시 켜졌다.

**확인 실험**: 절전을 런타임으로 끄자마자 중앙값 52.1 → 6.3 ms, 최대 302 → 127 ms.

## 원인 2 — 젯슨에 설정 앱 Wi-Fi 화면이 열려 있었다

절전을 끈 뒤에도 50 ms 넘는 핑이 15번 남았다. `iw event -t`로 보니 젯슨이 **15초마다 Wi-Fi 전체 스캔**을 하고 있었다
(2.4·5·6 GHz 전 채널, 한 번에 4~5초). 남은 튐이 스캔 시작 시각과 정확히 겹쳤다.

스캔을 요청한 건 젯슨에 열려 있던 **`gnome-control-center wifi`(설정 앱의 Wi-Fi 화면)**였다.
이 화면은 열려 있는 동안 주변 네트워크 목록을 갱신하려고 계속 스캔한다. 스캔하는 동안 무선이 다른 채널로 가 있어서 패킷이 밀린다.

**확인 실험**: 그 프로세스를 일시정지하자 40초 동안 스캔 0회, 최대 34.6 ms.

로봇 상태 화면(`status_display`)은 `iw dev ... link`로 신호 세기만 읽어서 스캔을 일으키지 않는다.

## 데스크톱도 같은 버그였다

데스크톱 동글도 9월에 끈 절전이 다시 켜져 있었다.

```
default-wifi-powersave-off.conf    ← 끄기
default-wifi-powersave-on.conf     ← 켜기  ← "off" < "on" 이라 나중에 읽혀서 이김
```

데스크톱→AP 구간은 이미 빨라서 이번 지연의 주원인은 아니었지만, 같이 고쳤다.

## 한 일

| 어디 | 무엇 | 연결 끊김 |
|---|---|---|
| 젯슨 `/etc/NetworkManager/conf.d/` | 끄기 파일을 `zz-gen2-wifi-powersave-off.conf`로 이름 바꿔 설치, 옛 `99-` 파일 제거, `nmcli general reload conf` | 없음 |
| 젯슨 | `iw dev wlP1p1s0 set power_save off` (재부팅 전까지 즉시 적용) | 없음 |
| 젯슨 | 열려 있던 설정 앱 Wi-Fi 화면 닫음 | 없음 |
| 데스크톱 | `ROBOT` 연결 프로필에 `802-11-wireless.powersave 2` 넣고 재연결 (sudo 없이 가능한 방법. 프로필 값이 전역 기본값보다 우선) | 몇 초 |
| PERSEVERANCE 저장소 | 설정 파일 이름 변경, `system/README.md` 설치 절차 수정, 로봇 쪽에 알리는 `comms/to-robot/2026-10-05_1714_desktop-wifi-latency-fix.md` — 커밋 `eda2720` | — |

지금 상태:

```
젯슨    NetworkManager --print-config  → wifi.powersave=2 (꺼짐)
젯슨    iw dev wlP1p1s0 get power_save → off
데스크톱 iw dev wlx98038eddfaa0 get power_save → off
```

젯슨은 재부팅해도 이제 꺼진 채로 올라온다 (설정 파일이 마지막에 읽힘). 실제 재부팅 시험은 하지 않았다.

## 다시 느려지면

1. **설정 앱 Wi-Fi 화면이나 네트워크 선택 창이 열려 있는지** 본다 (젯슨·데스크톱 둘 다). 쓰고 나면 닫는다.
2. 스캔 주기 확인: `iw event -t` — `scan started`가 15초마다 찍히면 스캔이 원인이다.
3. 절전 확인: `iw dev <인터페이스> get power_save` 와 `NetworkManager --print-config | grep powersave`
4. 핑은 시스템 `ping`으로: `/usr/bin/ping -D -i 0.2 -c 150 192.168.50.124`
   (이 PC는 PATH 앞에 nix의 GNU ping이 있어서 그냥 `ping`은 `-D` 옵션이 없다)

conf.d에 파일을 새로 넣을 때는 **이름이 패키지 파일(`default-…`)보다 뒤에 오는지** 확인하고, 반드시 `--print-config`로 실제 적용값을 본다.

## 전파 세기 (22:2x 추가 측정)

| 장비 | 신호 (0.5초 간격 10회) | 평균 | 속도 |
|---|---|---|---|
| 젯슨 (ROBOT5G) | -33 ~ -37 dBm | -32 dBm (비콘 -30) | 866.7 Mbps 양방향 — 5 GHz 80 MHz 2×2 최고 등급 |
| 데스크톱 동글 (ROBOT) | -32 dBm | -32 dBm | 144.4 Mbps — 2.4 GHz 2×2 최고 등급 |

젯슨 재전송 0.08 % (390만 패킷 중 3,201회), 실패 0회. 전파는 문제가 아니었다.

### AP(EAP225) 쪽에서 본 신호

EAP225 에 SSH 로 들어가 `enable` → `show station info` 로 읽었다 (펌웨어 5.2.4, 가동 8시간 30분, 부하 0.03).

| 단말 | 대역·채널 | AP 가 받은 신호 | 단말이 받은 신호 | 속도 (보냄/받음) | 연결 시간 |
|---|---|---|---|---|---|
| 데스크톱 동글 | 2.4 GHz · 11 | -32 dBm | -32 dBm | 144 / 143 Mbps | 5시간 19분 |
| **젯슨** | 5 GHz · 44 | **-47 dBm** | -32 dBm | 866 / 866 Mbps | 5시간 33분 |
| MacBook | 5 GHz · 44 | -43 dBm | — | 866 / 650 Mbps | 1시간 11분 |

- 잡음 -95 dBm 이라 젯슨 링크의 신호 대 잡음비는 약 48 dB. 아주 넉넉하다.
- **젯슨만 비대칭이다.** 젯슨은 AP 를 -32 dBm 으로 듣는데 AP 는 젯슨을 -47 dBm 으로 듣는다 (15 dB 차이).
  둘 다 송신 출력 22 dBm 으로 설정돼 있으니 젯슨 쪽 안테나 위치·방향(금속 프레임 안쪽 등)을 의심해 볼 만하다.
  다만 -47 dBm 도 최상 구간이고 양방향 모두 최고 속도(866 Mbps)라 지금은 성능에 영향이 없다. 로봇이 멀리 가면 젯슨 → AP 방향이 먼저 약해진다.
- AP 의 절전(Power Management)은 꺼져 있고, 비콘 누락·과도 재전송은 0.
- 2.4 GHz 쪽에서 다른 망의 프레임이 많이 잡힌다 (`Rx invalid nwid` 208,000 — 5 GHz 는 12,667). 11채널을 주변 망과 같이 쓰고 있다는 뜻이다.
  로봇 통신은 5 GHz(ROBOT5G)라 영향이 없고, 데스크톱 동글이 2.4 GHz 전용이라 이쪽만 해당한다.
- 채널 혼잡도(채널 점유율)는 이 CLI 로는 볼 수 없다. 웹 관리 화면에서 확인할 수 있다.
