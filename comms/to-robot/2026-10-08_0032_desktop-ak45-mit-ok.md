## 1. 데스크톱 시험 (2026-10-08, 사용자 + 데스크톱 에이전트)
- 어댑터: candleLight (gs_usb 1d50:606f) → `can0` 1 Mbit/s (`ip link set can0 up type can bitrate 1000000`). 필터 없이 모든 프레임 수신 (Python AF_CAN).
- 모터: **CAN ID 1**, MIT 펌웨어. MIT 진입 `FF FF FF FF FF FF FF FC`, 종료 `... FD`. MIT 에선 서보식 주기 업로드 없음 — **명령마다 응답 1 프레임**.
- **MIT 범위 (펌웨어 `CMESC_MIT_APP_AK45_10.bin` 역어셈블로 확인)**: P ±12.56 rad, V ±20 rad/s, KP 0–500, KD 0–5, T ±8 N·m.
  AK 공통값 (12.5 / 50 / 18) 이 아니다 — `motors.yaml` 의 `mit.*_max` 가 이 값인지 확인.
- 구동: kp 5, kd 0.3, ±0.3 rad 0.25 Hz 사인 → 추종 오차 ±0.06 rad, 토크 약 0.2 N·m, 36 °C, 오류 0.
- 스크립트: `comms/to-robot/attachments/ak45_mit/ak_test.py` (`listen | scan | hold ID`).

**바퀴 하나를 떼고, 이 MIT 성공 모터 (ID 1) 를 그 자리에 끼웠다.** 어느 쪽 바퀴 자리인지, ID 가 다른 바퀴 (ID 2) 와 겹치지 않는지 먼저 확인해 줘.

## 3. 부탁
1. 로봇 CAN 에서 이 모터로 `scan` 같은 시험 — **응답이 오면** 10-03 의 "응답 없음" 은 젯슨 쪽이 아니라 그때의 ID 2 모터 (펌웨어·파라미터) 문제였던 것.
   응답이 안 오면 젯슨 수신 쪽 (필터, master id, 응답 CAN ID) 을 데스크톱 스크립트와 비교.
2. 응답이 오면 바퀴 MIT 를 지연 관점에서 검토: 명령 → 응답이 같은 주기에 와서 서보 500 Hz 업로드보다 피드백이 신선할 수 있다. 명령→응답 시간을 재 줘
   (주 루프 지연 줄이기 — 8–10 Hz 진동의 원인. 지연 보상 예측기는 서 있기만 좋아지고 주행 시나리오는 나빠져서 답이 아니었다).
3. 바퀴 MIT 로 갈 경우 드라이브 current_limit (전엔 60 A) 와 CAN timeout (0) 을 먼저 안전값으로.
