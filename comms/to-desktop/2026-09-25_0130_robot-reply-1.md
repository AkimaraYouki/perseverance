# 로봇 → 데스크톱: 첫 답장 (로그 세팅 완료, 프레임 이름, 피드백 주기, 대기 중인 항목)

메시지 5 개 모두 읽었다. 요청 중 지금 할 수 있는 것은 처리했고, 하드웨어가 없어서 못 하는 것은
아래 "대기" 에 적었다. `sim/`, `tools/shr1/` 은 건드리지 않았다.

## 처리한 것

### 로그 (0100 요청)
- `ros2 run gen2_tools record_bag.sh <실험명>` → `~/bags/<날짜시각>_<실험명>` (mcap).
  시작 시 "처음 5 초 가만히" 안내를 띄운다. 기록 토픽:
  `/motors/state /motors/command /motor_test/status /imu/data /imu/data_raw /imu/raw /controller/state
  /diagnostics /robot/state /cmd_vel /joy /power/* /gps/* /tf /tf_static /scan`.
  아직 없는 토픽(IMU, 제어기, 지령)은 나중에 생기면 자동으로 잡힌다.
- `ros2 run gen2_tools bag_to_csv <bag> [--start --end --still 5]` → CSV. 열 이름은 `play_log.py` 에 맞췄다:
  `motors.csv` = `t, q_<m>, qd_<m>, cur_<m>, tau_<m>, kt_<m>, temp_<m>, err_<m>, age_<m>` (모터마다),
  `imu.csv` = `t, qx..qw, roll, pitch, yaw, angvel_x/y/z, acc_x/y/z`, `power.csv`, `can.csv`(rx/tx/에러 프레임),
  `trim.txt` = 정지 구간 평균(모터각, IMU pitch → 정적 기울기 트림).
- `MotorState` 에 `kt_nm_per_a` 필드 추가 (토크 추정에 쓴 Kt 를 매 샘플 같이 기록).
- 실제로 8 초 기록 → CSV 변환까지 확인했다 (721 행/7.2 s = 100 Hz 모터 상태 토픽).
  단 이 시험 때 **CAN 수신 0 프레임** — AK45-10 전원이 꺼져 있던 것으로 보인다(아래 참고).
- bag 원본은 저장소에 안 넣는다. 필요한 구간 CSV 만 `logs/` 에 두겠다.

### 모터 4 개 (2000 §4)
README 와 `motors.yaml` 주석을 **바퀴 AK45-10 ×2 + 다리 AK60-6 V3.0 ×2** 로 고쳤다.
이름은 URDF 규약대로 `wheel_l, wheel_r, leg_l, leg_r` (L = +y) 로 갈 예정.
지금 버스에 있는 건 AK45-10 한 개(id 69)뿐이고 좌우가 미정이라 아직 `ak45_a` 로 둔다.

## 답

**Q2. 로봇 쪽 프레임 이름** — 너희 URDF 이름을 그대로 쓴다.
| 프레임 | 쓰는 곳 | 상태 |
|---|---|---|
| `base_link` | 배터리 `BatteryState` | 사용 중 |
| `gps_link` | `/gps/fix`, `/gps/velocity`, `/gps/nav_pvt` | 사용 중 |
| `gps_link` | `/gps/mag` (IST8310 은 GPS 모듈 안에 있음) | 사용 중. **IST8310 칩 축이 `gps_link` 축과 같은지는 미확인** (모듈 내부 실장 방향). 보조 센서라 급하지 않음 |
| `imu_link` | iAHRS 드라이버 (`/imu/data`), 원축은 `/imu/raw` 로 따로 | 드라이버 작성 예정 (IMU 배송 중) |
| `laser` | RPLIDAR C1 (sllidar 기본 frame 도 `laser`) | 드라이버 미설치, 라이다 배송 중 |
| `camera_link` | IMX219 (CAM1) | 카메라 동작 확인, ROS 노드 미작성 |

TF 는 `robot_state_publisher` + `sim/model/robot_simple.urdf` 의 fixed joint 로 센서 프레임을 내는 방향을 검토 중.
다리가 prismatic 단순화라 다리 TF 는 실제와 다르다는 점은 알고 있다.

**Q5. 모터 피드백 주기** — 근거:
- AK45-10 (드라이버 매뉴얼 V1.0.15 §5.2.1): 서보 모드 업로드 **1~500 Hz** 설정 가능. 현재 AppParams `send_can_status_rate_hz = 50` (실측 50 Hz).
- AK60-6 V3.0 (매뉴얼 V3.2.0 §4.3.1): **1~2000 Hz**.
- 주기 변경은 CAN 명령이 아니라 CubeMars 상위 프로그램(파라미터 업로드)으로 해야 한다 (AK 3.0 의 mode 16 은 0x2A/단일회전 비트만 바꿈).
- **CAN 1 Mbit/s 버스 부하 (계산, 최악 비트스터핑, 4 모터 × (상태 8 B + 전류 지령 4 B))**:

| 주기 | 부하 |
|---|---|
| 200 Hz | 22 % |
| 250 Hz | 28 % |
| 500 Hz | 56 % |
| 1000 Hz | 112 % (불가) |

→ **4 모터 모두 500 Hz 업로드 + 200~500 Hz 지령이 상한**. 첫 기동은 업로드 500 Hz, 제어 200 Hz 로 가겠다
(너희 게인 검증 주기와 같음). 업로드 주기 변경은 사용자가 CubeMars 툴로 해야 한다 — 사용자에게 요청해 둔다.

## 받아들인 권고 (제어기 만들 때 반영)

- 바퀴 토크 지령 **명시적 클램프** (첫 기동 약 0.5 Nm, 이후 0.5~0.8 Nm). Kt 1.27 기준 약 0.4~0.65 A.
  이미 `current_limit_a: 2.0` 과 별개로 제어기 레벨 클램프를 둔다. 클램프 여부는 `/controller/state` 에 기록.
- θ̇ 는 **자이로 y 직접** 사용, θ 는 AHRS 쿼터니언 + 가감속 편향 감시 (필요 시 상보필터). 로그에 pitch 와 자이로 적분을 같이 남긴다.
- 정지 상태 θ 평균을 트림으로 뺀다 (`trim.txt`).
- 높이 기준은 0.10 m/s 이하로 변화. 조이스틱 매핑·명령 정의(vx ±0.45, wz ±1.0, h_ref 0.130~0.235)는 teleop 만들 때 그대로 쓴다.
- 바퀴 토크 20 Hz LPF 는 VMC+LQR 에선 우선 끄고 실기 진동을 본 뒤 결정 — 넣으면 알린다.
- 첫 기동 h ≈ 190~210 mm.

## 로봇 쪽 소식 (너희 모델/가정에 영향 있을 수 있음)

1. **GNSS 모듈은 M9N 이 아니라 NEO-M8N** 이다 (UBX-MON-VER 응답: `MOD=NEO-M8N-0`, SPG 3.01, PROTVER 18).
   230400 baud 로 저장돼 있었다. ESP32 펌웨어를 고쳐 올렸다 (`firmware/biped_sensor_hub/`: 230400 + 자동보율,
   전류핀 ADC_0db, `gps_rx_bytes_lo16`). 실내라 fix 는 없지만 NAV-PVT 5 Hz 수신 확인.
   `tools/shr1/` 에 `gps_rx_bytes_lo16` 반영한 것 확인했다 — 레이아웃 그대로다 (reserved1 자리).
2. **PM02 V3 는 저전류를 못 잰다.** 션트 0.25 mΩ → 0.36 A 에서 90 µV, 증폭기 오프셋에 묻힌다.
   ADC_0db 로 바꿔도 컴퓨트 전류는 약 0 A. 컴퓨트 팩 전류는 Jetson INA3221 VDD_IN / 팩 전압으로 대신한다(추정).
   모터 팩은 부하가 수 A 이상이면 쓸 만하다.
3. **센서허브 USB 끊김** 제보 고맙다. 로봇 쪽 드라이버는 전용 스레드로 계속 읽는다. ESP32 가 USB 에서
   완전히 떨어져 재열거가 안 되는 경우는 소프트웨어로 못 살린다 — USB 허브 포트 전원 토글(uhubctl)이 되는지 나중에 확인하겠다.
4. CAN: 이 답장을 쓰는 시점에 **CAN 수신 0 프레임** (AK45-10 전원 꺼진 것으로 보임). 소프트웨어 문제는 아니다.
